# 城市集中供热管网与换热站运行管理平台

面向一次二次管网台账、换热站运行、水力平衡调节、热计量抄表、抢修处置、停暖通知与热费结算的一体化城市集中供热运行管理工作台。

这是一个**纯前端**管理平台：Vue 3 + Vite + TypeScript，仓库里没有后端服务。业务数据由
`frontend/src/data/` 下的本地数据层提供：首次打开用示例数据播种，之后的登记、筛选与状态流转
结果都持久化在浏览器 `localStorage` 里，刷新或重开浏览器都还在。dev server 已关掉自动打开页面，
启动后按终端打印的地址手工打开。

## 目录结构

```text
.
├── frontend/                 Vue 3 + Vite + TypeScript 前端（唯一运行单元）
│   ├── src/views/            每个业务模块一个页面
│   ├── src/api/local-service.ts   本地数据服务：列表、筛选、动作流转、导出
│   ├── src/data/             模块元数据 / 示例数据 / localStorage 持久化
│   ├── src/stores/           会话与筛选状态
│   └── vite.config.ts        dev server 配置（open: false，无 /api 代理）
├── .gitignore
└── docker-compose.yml
```

## 启动

```bash
cd frontend
npm install
npm run dev
```

前端默认监听 `http://127.0.0.1:5173/`，dev server 不会自动打开浏览器，需要自己访问。

生产构建：

```bash
cd frontend
npm run build
```

## 约定

- 每个模块的页面在 `frontend/src/views/<模块>/index.vue`，页面只负责渲染，读写统一走
  `frontend/src/api/local-service.ts`。
- 字段、状态、动作与流转目标集中在 `frontend/src/data/modules.ts`；示例数据在
  `frontend/src/data/seed.ts`。
- 字段、状态、分组/分栏/分页与册子导出的规则在 `frontend/src/api/valve-grouping.ts`，台账页、
  检查单页与导出册子都引用同一份。
- 状态流转只允许在 `local-service.ts` 里改，页面组件不做业务判断。
- 想回到初始数据：清掉浏览器里 `district-heating:entries` 这一项，或调用 `resetModule(模块)`；
  阀门井检查回写的探漏待复核清单存在 `district-heating:leak-reviews`。

## 阀门井检查记录分组（阀门井检查单）

阀门井台账（`/valvewell`）与阀门井检查单（`/valvewell/inspection`）取的是同一份数据
（`valvewell` 记录集合），只是组织方式不同：

- **分栏分组**：检查单按「井盖状况」分栏，每栏内按「养护措施」聚成一组，组内按检查日期倒序；
  检查日期缺失的井不参与检查分组，单独沉底到「待检查」栏便于安排补查。
- **整组翻页**：以整组为最小翻页单位（每页约 8 条记录的容量），跨页翻页任何一组都不会被拆到两页；
  单组超过一页容量时独占一页。
- **组导航与跳组**：页顶分组胶囊可直接跳到任意一组；「井编号跳组」下拉可直接落到该井所在组并高亮。
- **只看尚未养护的井**：同一口井以最新一条检查记录判定，台账页和检查单都可一键筛出还没养护的井，
  不必逐页翻找。
- **打包册子下载**：把当前筛选结果打包成一份自包含的可打印 HTML 分组册
  （按井盖状况分章、养护措施分节、组内日期倒序），导出即下载，打印后即可带走下发。
- **受理规则**：检查报送必须有检查日期（缺失不予受理）、井编号与井盖状况；同一口井、同一天的重复
  报送只认第一次，后续报送会被退回并指明第一次报送的记录号。兼容既有的「提交检查 / 确认养护 /
  提出维修」逐行动作。
- **结果回写**：受理一条检查报送后，会在管网探漏页的「阀门井检查回写 · 待复核清单」生成一条待复核
  记录；探漏班组「确认」后会在探漏台账登记一条「需复探」记录，「排除」则仅标记、不建单。
